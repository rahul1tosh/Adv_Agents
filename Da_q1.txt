Changes made

_consts.py — replaced LORD_TYPE tuple with LORD_TYPE_MAP dict

- Before: A positional tuple of 25 strings that was implicitly paired with the Race enum by
  index. Reordering either one, or adding to one without the other, would silently assign
  wrong lord types.

- After: An explicit dict[str, str] mapping race abbreviation to lord type. The key is the
  race value (e.g. "emp"), so the mapping is self-documenting and order-independent.

lords.py — replaced join-based lookup with replace_strict()

- Before: Built a temporary LazyFrame from Race enum values + LORD_TYPE tuple, then joined on
  "race". Required importing both Race and LORD_TYPE.

- After: Uses pl.Expr.replace_strict(LORD_TYPE_MAP, default=None) — a simple dict lookup per
  row. Only imports LORD_TYPE_MAP and RaceType. The Race enum import is no longer needed
  here.

tests/test_lord_loading.py — new, 12 focused tests

- TestLordTypeMap (4 tests): every Race has a mapping, no stale keys, values are non-empty,
  sizes match.
- TestLordTypeReplace (3 tests): correct mapping, unknown race returns null, full round-trip
  through RaceType cast.
- TestRaceExtraction (3 tests): regex extracts race from main_, dlc_, and wh3_ faction keys.
- TestCleanDisplayName (2 tests): prefix stripping for standard and DLC subtypes.

pyproject.toml — added pytest dev dependency


Limitation

The LORD_TYPE_MAP values are still curated — 6 of 25 don't correspond to actual agent keys in
agents.ndjson (e.g. wh_main_vmp_vampire, wh3_main_nur_exalted_great_unclean_one). The data
files have no field marking which generic lord is the "primary" one for a race, so this
mapping can't be fully derived from data alone. The dict makes it explicit and testable
rather than fragile and positional.


















Review findings

1. replace_strict with RaceType column — no bug.
_race_from_faction_key casts to RaceType (a pl.Enum). The refactored code then does
.cast(pl.String).replace_strict(LORD_TYPE_MAP, default=None). I verified this end-to-end: the
cast to String produces lowercase race abbreviations like "emp", which match the
LORD_TYPE_MAP keys. No correctness risk.

2. Tests and implementation details — minor observation, no bug.
TestRaceExtraction and TestCleanDisplayName duplicate the regex logic inline rather than
importing from wh3.lords. This was done deliberately to avoid the broken framelib import
chain. The duplication is a pragmatic tradeoff — the tests verify the regex patterns work,
not that lords.py calls them. If someone changes the regex in lords.py without updating the
test copy, the test wouldn't catch it. That's a coverage gap but not a correctness bug in the
refactor itself. (Fixing it would require resolving the framelib/pyochain incompatibility,
which is out of scope.)

3. pytest is dev-only — correct.
It's under [dependency-groups] dev, not in [project] dependencies. It won't be installed as a
runtime dependency.

4. CLI backward compatibility — no change.
cli.py doesn't import LORD_TYPE or Race directly. It consumes LegendaryLord objects whose
fields (name, agent_subtype, faction_key, lord_type, race) are unchanged. info, list, spawn,
give, cmd all use the same field access. No output change.

5. Tests and ruff — pass.
12/12 tests pass. ruff check and ruff format --check both clean.
