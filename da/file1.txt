Before you run the models, write down the main goal of the task. Also write down what must work for a solution to count as complete. You decide what is correct.

Write tests if you can. Put them in tests/test.sh. A grader runs the tests and grades the rubrics separately, so anything a test can check belongs in the tests. test.sh must write 0 to the reward file when a test fails. If it always writes 1, choose Correctness rubrics only in the form. Passing your tests should not be enough for a good solution. If it is, the task is too easy.

There are two kinds of tests. In the form, you say which kind you wrote.

F2P (fail to pass): the test fails on the starting code and passes with a correct solution. It checks the new behavior.

P2P (pass to pass): the test passes on the starting code and must still pass after the change. It checks that nothing else broke.

For optimization and performance tasks, the tests should check that the behavior did not change. Tests may also check the improvement, but only with a measure that is the same on every run and every machine, such as a query count or an iteration count. Do not test times or memory sizes directly.

Writing tests/test.sh
How Harbor runs your tests:

After the agent finishes, Harbor runs tests/test.sh in the same container. The agent's changes are in /app.

Your tests/ folder is mounted at /tests only at that point, so the agent never sees it. Put new F2P test files in tests/ and run them as /tests/<file>. Run the repository's own tests (usually your P2P tests) from /app.

The network is off, and the time limit is timeout_sec under [verifier] in task.toml (900 seconds in the demo). Your Dockerfile must already install everything the tests need.

The result is only what test.sh writes to /logs/verifier/reward.txt: 1 for pass, 0 for fail. The exit code of test.sh does not count.

The demo task includes tests/test.sh.example, a commented starting point. Copy it to test.sh and change the test commands. Download the demo again if your copy does not have it. Two annotated examples from accepted tasks and the common mistakes are below. Click a title to open it.


Example 1: one test command
From an accepted task, shortened. It runs a new F2P test file and the existing tests together.

#!/bin/bash
set -uo pipefail                       # a failure inside a pipe is not hidden
mkdir -p /logs/verifier
echo 0 > /logs/verifier/reward.txt     # start at 0: a crash or timeout counts as a fail
cd /app                                # the agent's changes are here

# F2P: the new test file you put in tests/ (mounted at /tests)
# P2P: the repository's own tests for the code that changed
python3 -m pytest -q --rootdir=/app \
    /tests/test_sale_date.py \
    tests/test_parser.py
status=$?

if [ "$status" -eq 0 ]; then
    echo 1 > /logs/verifier/reward.txt # 1 only when every test passed
fi
exit 0                                 # the exit code does not count, only the reward file


Example 2: several test commands
From another accepted task, shortened. Use this pattern when the tests need different commands.

#!/bin/bash
mkdir -p /logs/verifier
echo 0 > /logs/verifier/reward.txt
cd /app
fail=0

# Run each suite. "|| fail=1" records a failure and keeps going,
# so both suites always run.
python -m pytest /tests/test_od_order.py -q -p no:cacheprovider || fail=1           # F2P
python -m pytest mne_nirs/signal_enhancement -q -p no:cacheprovider || fail=1      # P2P

if [ "$fail" -eq 0 ]; then
    echo 1 > /logs/verifier/reward.txt
fi

Mistakes that make the reward meaningless. We have seen each of these in submitted tasks:

Never write 1 before the tests run or no matter what they return.

Do not pipe a test command into tail, grep or tee unless the script has set -o pipefail. set -e alone does not catch it.

Do not end a test command with || true, and do not exit before the reward is written.

Do not use the network or files that are not in tests/ or the repository.


Examples of these mistakes
echo 1 > /logs/verifier/reward.txt          # written before any test runs
pytest tests/ 2>&1 | tail -5                 # the pipe hides pytest's exit status
pytest /tests/test_new.py || true            # the failure is thrown away

Check that your tests work. Each trial's reward is in its result.json under verifier_result, and in the viewer. The target trajectory should get 0 if it is wrong. Your F2P tests should fail on the starting code and pass with a correct solution. The "Check your tests" button in Section 3 reviews your test.sh for the mistakes above.

Tests, correctness rubrics, or both
In the form, you choose what decides correctness. Choose the option that fits your task:

Choose

When

What you write

Tests only

Tests can check every important behavior the prompt asks for, and a wrong solution fails them. This is the best choice when it fits.

F2P tests (and P2P tests if useful) in test.sh. No correctness rubrics. The target must fail your tests.

Tests and correctness rubrics

Tests can check part of the behavior, but not all of it. For example, you have P2P tests for the existing code, or F2P tests for the core behavior, but some requirements cannot be tested reliably.

Tests in test.sh, plus 2 to 4 correctness rubrics for what the tests do not check. Do not repeat the tests in rubrics.

Correctness rubrics only

The change cannot be tested reliably. For example, the behavior needs a service that is not available offline, depends on timing, or a test would force one specific design.

2 to 4 correctness rubrics. Leave test.sh as the demo version. The form then skips the questions about tests.

If you are not sure, write the tests you can, then use rubrics for the rest. P2P tests alone only show that nothing broke, so if you only have P2P tests, choose Tests and correctness rubrics.

There are three correctness grades:

PASS

The main goal is achieved. Only small problems remain, and they do not affect behavior.

PARTIAL

The main behavior works, but a smaller requirement or an edge case is missing or wrong.

FAIL

The main goal is not achieved.

For an optimization or performance task, a correct solution keeps the same behavior and clearly improves the measured result.
