Overview
You will write a difficult coding task and run two AI models on it. Then you compare their work. The best tasks are fair, but a strong model still gets them wrong. You must show the mistake with evidence that anyone can check.

Each step below has a matching section in the form, with the same number. Open each step when you reach that section.

Choose a codebase that you know well.
Write the task and package it for Harbor.
Write down what a correct solution must do.
Run the models and upload the results.
Find the mistakes in each trajectory. Write correctness rubrics if you use them.
Rate both trajectories on eight dimensions.
Write rubrics for the dimensions.
Give overall scores and choose the better trajectory.
Key terms
Trajectory

One model's complete attempt at your task: every command it ran, everything it wrote, and its final code changes.

Target trajectory

The trajectory that must fail, in both of its rollouts. Each rollout needs a correctness failure (Step 5). Your task data tells you which one it is.

Rollout

One run of one model on your task. Harbor saves each rollout as a trial folder. The target model has 2 rollouts: one in the main job and one in the target rollouts job.

Loss pattern

A kind of mistake that models often make in our evaluations, for example gaming the checks. Step 7 lists them.

Rubric

One clear check that a trajectory passes or fails, for example "Fail if: a test was deleted".

Harness

The program that runs the model inside your task environment, for example OpenCode.

Alias

A code name for a model. The real model name is hidden.

You may use AI coding tools to read code and run tests. You must write all of your answers yourself. If you use an external AI tool such as ChatGPT to write your answers, you will be removed from the platform. The built-in buttons in the form, such as Suggest preflight checks and Check rubric quality, are fine to use.

Known Technical Issues (check here before asking in chat)


Step 1: Choose a codebase
Choose a repository in a programming language and field that you work in. You should be able to explain why one solution is better than another, even when both solutions pass the same tests.

We especially want three kinds of tasks. Only choose them in areas where you have real experience:

Refactoring, migration and code cleanup, especially work that needs careful git history, such as merging branches, resolving conflicts or cherry-picking commits.

Debugging in distributed systems and machine learning systems, especially when the cause has to be found in logs, data or reports.

Performance improvements, such as lower CPU or resource use, memory leak fixes, or faster database queries. The improvement must show on any Linux machine (Step 2).

Other kinds of tasks are still welcome.

Rules for the code
Code from other people must have a permissive license: MIT, Apache 2.0, or BSD. Read the license file in the repository. If there is no license file, you cannot use the repository.

For a public repository, the Dockerfile should download the code at one fixed commit (the full 40-character hash). Do not copy the code into codebase/ unless you need to.

You may also use your own local code. Put it in environment/codebase/. It must be big enough that two good solutions can have different designs. A single file is too small.

Delete files with instructions for AI agents, such as AGENTS.md. Some harnesses give these files to the model.

You may use the same repository for more than one task. Each task must be a different problem in a different part of the code.



Step 2: Write the task
Write the prompt in plain language. Use normal sentences, without headings or numbered requirements. You may use a public issue or pull request as an idea. Your task must be clearly different from it, because the models have probably seen the original.

Make it hard and fair
We need tasks where a strong model gets the main behavior wrong. Every task must require reading or editing at least 15 files to solve it correctly. These kinds of tasks often cause real mistakes:

Work that touches many files, where one change has to be repeated correctly in every place that uses it.

Behavior that depends on a detail in the existing code, such as a rule about the order of operations.

Edge cases that come from the subject area, such as numeric precision.

Bugs where the easy fix hides the error but does not fix its cause.

Bugs whose cause has to be found in logs, data or reports, for example in a distributed or machine learning system.

Refactors and migrations that must stay consistent everywhere and keep the existing behavior, including ones that need git work such as resolving merge conflicts or cherry-picking commits.

Do not try to trick the model. Every requirement you grade must be in the prompt or be clear from the code. The agent has no internet access while it works, so the task must not need it.

Open-ended optimization and performance tasks
You may write a task with an open target, such as "make this solver use as few iterations as possible", or a performance task, such as cutting CPU time or memory use, fixing a memory leak, or speeding up a database query. Tell the agent what to measure and how to measure it inside the container. Also tell it what must not change, for example that the existing tests must still pass. A simple solution and an expert solution should give very different results.

The improvement must show on any Linux machine, not only on yours. Prefer measures that do not depend on the hardware, such as the number of queries, iterations, allocations or rows read, or memory that keeps growing. If you measure time, compare with the starting code in the same container, and only ask for a large improvement, such as several times faster.

2. Validate the task
The agents have no internet access. If a tool is missing, the comparison is not fair. validate_task.py checks this before you run the models. It builds your image, runs your checks with the network turned off, and tests that the code changes will be saved. It does not call any model.

First, write your checks in preflight.toml in your task folder. If your code is in a public repository, the "Suggest preflight checks" button in Section 2 can write a first version for you. Each check is a command that must succeed inside the container. Use commands that your task really needs, such as importing your project and running the tests that the task touches. For example:

[[checks]]
name = "Project and test imports"
command = "python3 -c 'import my_project, pytest'"

[[checks]]
name = "Parser tests"
command = "python3 -m pytest -q tests/test_parser.py"
timeout_sec = 180

Then run the script from the folder that contains your task and the worker tools:

./ummon-worker-tools/validate_task.py <your task folder>

If you see Permission denied, run chmod +x ummon-worker-tools/*.py once. You can also run uv run --script ummon-worker-tools/validate_task.py <your task folder>. Do not run it with python3, because your system Python may be older than 3.12.

The last line should start with PASSED. If it says BLOCKED, read the findings above it, fix the task, and run the script again. Run it again every time you change the task or the checks. The script saves its logs in results/preflight/. Do not put that folder in your zip files.

Do not end a check with true or hide its errors. A check that always passes does not test anything.

3. Run the job
harbor run \
  --config agents.yaml \
  --path <path to your task folder> \
  --env-file proxy.env \
  --jobs-dir ./jobs \
  --job-name <a name you choose> \
  --n-concurrent 2 \
  --yes

Both trials are saved in one job folder under jobs/. This is the main job. A trial is one rollout of one model. If a trial stops with an error, run the same command again. Harbor runs only the missing trial.

To replace one trial, use ./ummon-worker-tools/rerun_trial.py jobs/<job-name> <model> --reason "...". For <model>, use the model name from your task data, for example gemini/brawne, or the exact trial folder name. In the target rollouts job, use the exact trial folder name. The script finds proxy.env in the current folder or next to jobs/. Use --env-file if it is somewhere else. Add --dry-run to see what it will do first. If you change the task in any way, start new jobs: run the main job and the target rollouts again.

4. Run the target rollouts
Run the target model, gemini/brawne, 1 more time on the same task folder:

uv run --script ummon-worker-tools/run_target_rollouts.py \
  --config agents.yaml \
  --model gemini/brawne \
  --rollouts 1 \
  --path <path to your task folder> \
  --env-file proxy.env \
  --jobs-dir ./jobs \
  --job-name <your main job name>-target

The script keeps only the target's agent from agents.yaml (it does not change your file) and runs harbor run with --n-attempts 1. The trial is saved in its own job folder. Zip it and upload it in Section 4. If the rollout stops with an error, run the same command again. Add --dry-run to see what it will do first. Use your final task folder: Validate deliverables checks that both jobs ran the same task. If your machine can run three trials at once, you can start it at the same time as the main job, after validate_task.py passes.

Run the extra rollout once. If it does not have a correctness failure, do not run it again or replace it to get a different result. Change the task instead (Step 5), then run both jobs again. Only rerun or replace a trial that stopped with an error.

5. Read the results
harbor view jobs opens a viewer in your browser (usually http://127.0.0.1:8080). To see which trial is A and which is B, look at agent.model_name in each trial's config.json. You compare the two trials in the main job. Use the target rollouts job only to confirm the target's failure (Step 5). Do not swap a target rollout into the pair. You will use these files:

<trial>/agent/trajectory.json: everything the agent did and said

<trial>/artifacts/patch.diff: the agent's code changes

<trial>/trial.log: the log of the run

Every trial in both jobs must finish normally. The Exceptions column in the viewer must be empty.
